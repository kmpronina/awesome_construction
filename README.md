# Awesome Construction — мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании. Постановщик ставит задачи по объектам (стройкам), исполнители берут их в работу и отправляют на проверку. Каждая смена статуса сохраняется в истории.

Главный принцип: **все правила доступа живут в базе данных**, а не только в интерфейсе. Интерфейс лишь скрывает недоступные действия; даже прямой запрос к Supabase в обход приложения упрётся в те же проверки.

## Стек

- **Next.js 16** (App Router) + **React 19** + **TypeScript**
- **Supabase**: Postgres, Auth, Row Level Security, функции и триггеры на PL/pgSQL
- **Tailwind CSS 4**, Radix UI (меню, выпадающие списки), Formik + Yup (формы), Zustand (состояние пользователя), Sonner (уведомления)
- Деплой: **Vercel**

## Возможности

| Роль        | Что может                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Постановщик | создаёт, редактирует и удаляет объекты и задачи; назначает исполнителя; принимает задачи или возвращает на доработку; видит все объекты и задачи |
| Исполнитель | видит только свои задачи и объекты, в которых у него есть задачи; берёт задачу в работу и отправляет на проверку                                 |

Экраны: вход по email и паролю, список объектов, карточка объекта со списком задач, карточка задачи (данные, кнопки доступных действий, история), «Мои задачи» для исполнителя, создание и редактирование объектов и задач.

### Статусы и переходы

| Из статуса   | В статус                 | Кто может               | Условие                |
| ------------ | ------------------------ | ----------------------- | ---------------------- |
| —            | Новая (`new`)            | постановщик             | при создании задачи    |
| Новая        | В работе (`in_progress`) | назначенный исполнитель | —                      |
| В работе     | На проверке (`review`)   | назначенный исполнитель | —                      |
| На проверке  | Принята (`accepted`)     | автор задачи            | —                      |
| На проверке  | На доработке (`rework`)  | автор задачи            | комментарий обязателен |
| На доработке | В работе                 | назначенный исполнитель | —                      |

Другие переходы запрещены. Правила хранятся в таблице `status_transitions`, а проверяются функцией `change_task_status` в базе.

## Как защищены данные

- **RLS включён на всех таблицах.** Без подходящей политики доступ закрыт.
- **Исполнитель** читает только задачи, где он назначен исполнителем, и только объекты, где у него есть задачи. Изменять задачи напрямую он не может.
- **Постановщик** читает всё, но изменять и удалять может только объекты и задачи, автором которых является.
- **Смена статуса** возможна только через функцию `change_task_status`. Она проверяет участие пользователя в задаче, разрешённость перехода, роль и обязательный комментарий, затем меняет статус и пишет запись в историю. Прямой `update` колонки `status` запрещён правами на колонки.
- **История (`task_history`)** не имеет политик на вставку, изменение и удаление: через API её нельзя подделать, изменить или удалить. Записи добавляют только функции и триггеры базы.
- **Права на колонки**: у задачи через API можно изменить только название и описание, у объекта — название и адрес. Автор, исполнитель и объект задачи задаются один раз.
- **Триггеры** проставляют автора, начальный статус и дату создания сами, не доверяя данным из запроса; запрещают редактировать принятую задачу и удалять объект, в котором есть задачи.
- **Открытая регистрация отключена**, пользователей создаёт администратор в панели Supabase.
- **Секретные ключи** (`service_role` и подобные) не используются ни во фронтенде, ни на сервере приложения и не хранятся в репозитории. Приложение работает только с публичным ключом, а все запросы — от имени вошедшего пользователя.

## Структура проекта

```
src/
  actions/        запросы к Supabase и серверные функции (создание, изменение, удаление, смена статуса)
  app/            маршруты Next.js: (auth) — вход, (dashboard) — страницы приложения
  components/     views — страницы, forms — формы, cards, layouts, ui — базовые компоненты
  libs/supabase/  клиенты Supabase для браузера, сервера и proxy (обновление сессии)
  stores/         Zustand-стор текущего пользователя
  types/          типы приложения и сгенерированные типы базы (database.ts)
  proxy.ts        обновляет сессию и перенаправляет гостей на /login
supabase/
  migrations/     миграции базы: таблицы, функции, триггеры, политики RLS, справочники
  seed.sql        тестовые данные (профили, объекты, задачи)
```

## Запуск локально

### 1. Требования

- Node.js **20.9** или новее
- Yarn 1 (`npm i -g yarn`)
- Аккаунт Supabase (бесплатного тарифа достаточно)

### 2. Установка

```bash
git clone <ссылка на репозиторий>
cd awesome_construction
yarn
```

### 3. Проект Supabase

1. Создайте проект в [Supabase](https://supabase.com).
2. Примените миграции:
    ```bash
    npx supabase login
    npx supabase link --project-ref <project-ref>
    npx supabase db push --remote
    ```
    `project-ref` — часть адреса проекта: `https://<project-ref>.supabase.co`.
3. Отключите регистрацию: **Authentication → Sign In / Providers → Allow new users to sign up** — выключить.
4. Создайте пользователей: **Authentication → Users → Add user → Create new user**, с отметкой **Auto Confirm User**. Нужны минимум один постановщик и два исполнителя.
5. Добавьте тестовые данные: откройте `supabase/seed.sql`, при необходимости поправьте email пользователей и выполните его в **SQL Editor**. Скрипт создаёт профили с ролями, объекты и задачи. Профиль без роли не увидит в приложении ничего — так работают политики.

### 4. Переменные окружения

Скопируйте `.env.example` в `.env.local` и заполните значения из **Project Settings → API Keys** (или кнопки **Connect**):

```
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Нужен только публичный (publishable) ключ. Секретный ключ проекту не нужен.

### 5. Запуск

```bash
yarn dev
```

Приложение откроется на [http://localhost:3000](http://localhost:3000).

## Деплой на Vercel

1. Импортируйте репозиторий в Vercel: **Add New → Project**. Next.js и Yarn определятся автоматически.
2. В **Settings → Environment Variables** добавьте `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
3. Запустите деплой.
4. В Supabase укажите адрес приложения: **Authentication → URL Configuration → Site URL**.

## Как проверить защиту в обход интерфейса

Войдите в приложение под исполнителем и выполните запросы от его имени, например через `supabase-js` в консоли или любым HTTP-клиентом с его токеном:

- прочитать задачу другого исполнителя — вернётся пустой результат;
- изменить `status` задачи напрямую через `update` — отказ по правам на колонку;
- вызвать `change_task_status` с запрещённым переходом (например, `new → accepted`) — ошибка из базы;
- вставить, изменить или удалить запись в `task_history` — отказ RLS.

## Решения и допущения

- Объект и исполнитель задачи задаются при создании и потом не меняются.
- Редактировать и удалять объект или задачу может только её автор; остальные постановщики видят всё, но только читают.
- Менять статус со стороны постановщика может только автор задачи.
- Принятую задачу нельзя редактировать.
- Удаление задачи мягкое и необратимое: задача остаётся в базе с отметкой времени удаления и скрывается от всех, история сохраняется.
- Объект, в котором есть задачи (в том числе удалённые), удалить нельзя — чтобы не потерять их историю.
- Комментарий можно оставить к любому переходу; обязателен он только при возврате на доработку.
- Время в истории показывается в UTC: страницы отрисовываются на сервере.
